一、背景：为什么是 Jump，为什么是 quant

Jump Trading 是一家 1999 年成立于芝加哥的自营量化交易公司，如今在 12+ 个城市设有办公室，在全球多资产、多时间尺度上做电子化交易。它没有外部投资人，所有 P&L 来自自有资金。这种商业结构决定了一件事：任何"多花一块钱算力"或"晚出一毫秒"都要被立刻量化在业绩上。

量化金融给通用 agent 架构施加的约束，被 Loren 归纳为三组严苛条件：数据非平稳、延迟预算紧、时序推理的细微错误会让整条研究管线失效。这三点共同决定了今天的 talk 主线：在 quant 上做 agent，benchmark 方法学比模型选型更重要。

二、Loren：单 agent → harness → multi-agent 的演进

2.1 基线与"complexity needs to be earned"

Loren 反复强调的元规则是：先有一个单 agent + 单 harness 的基线——任何更复杂的方案都必须能改善指标，否则就是 noise。"complexity needs to be earned."

可调维度被画成一个 k-dimensional hypercube（模型 / Harness / Tools / Context / Workflow / Budget / 问题类型）。Loren 把范围收敛到一窄切片——market analyst 任务——然后开始做对比。

2.2 Point-in-time Eval：为什么公开 benchmark 不够

Loren 把 quant 上公开 benchmark 不足的原因归纳为三件事：

  • Temporal leakage：模型预训练里见过未来数据；backtest 在 cutoff 前看着漂亮，cutoff 后立即崩。他用一句话点出本质："Time travel is the default failure mode."
  • 私域 workflow 与数据：内部数据 schema、问数习惯、research workflow 在任何公开 benchmark 里都没有对应。
  • 任务类型的差异：金融任务的多模态（订单簿、内部状态、新闻、基本面）和时序耦合是独特的。

为此 Jump 搭了一套 point-in-time agent eval pipeline（挖真实对话 → 标注 point-in-time 信息 → LM 生成 eval case → 存全 artifacts）。

2.3 SpaceX IPO 案例：从抽象到具体

Loren 用一个具体例子把方法论落到地面：SpaceX 预期 6/12 IPO，问"首日收盘价"。

  • 冻结 point-in-time："这道题是 6/5 提出的，比 IPO 早一周"；要求给出 evidence、uncertainty quantification、可追溯 artifacts。
  • 模型轴：固定 harness 换模型——新版 frontier 模型更好（4.8 > 4.7 …）。
  • Harness 轴：两个 custom harness 的端到端分数略差于 baseline，但 trace analysis 显著更好——把两个 orthogonal 的 harness 合并（h1+h2），最终 trace 和 end-to-end 同时超过 baseline。

Takeaway：更好的模型不是处处更强。在窄子任务上，更小、更专门的模型或 harness 仍能赢过 frontier。

三、Lucas：哲学、工程与多 agent 的"何时该上"

3.1 Multi-agent 不是默认答案

Lucas 开场就引用 ICLR 那篇 talk 的观点："throw away your multi-agent system unless you have a really good reason for it." 但他也承认业界（Claude、CodeX 等）正在默认打包 sub-agent。真正的问题是哪种模式匹配哪种任务：

  • Decentralized：适合工具调用（多个 agent 各自 fetch、互不依赖）。
  • Orchestrator-Worker (centralized)：适合结构化、可并行的推理——前提是子 agent 有清晰 roles / personas。
  • Single agent：适合强 sequential 任务。
  • Hybrid：介于以上几种之间。

3.2 Effort Ladder：什么时候该往哪一层走

他把"做 agent"的努力画成一个梯子：单 prompt → 加 prompt/context → 加 tool → 改 harness/子 agent → post-train → mid-train → 预训练。每一层都比上一层贵得多；每上一层都应该是因为"下一层已经不够了"。他的元问题："你在为 specialization 什么？"——答不上来就别 specialize。

3.3 三维度：performance / latency / cost

  • Performance：选最适合子任务的模型或 harness——不一定要 frontier。
  • Latency：注意是 time-to-last-token（完整分析完成、可行动的时间），不是 time-to-first-token。
  • Cost：trading firm 通常对模型花费不敏感，但 Jevons paradox 在起作用——成本下降让我们能跑更多调用。

3.4 多 agent 合并的信息上界

Lucas 给了一个信息论结果（"don't try to use this in practice"——Bonferroni on steroids）：系统的 overfit gap 的上界由 token 携带量决定，与系统复杂度无关。含义很直接：把系统做复杂不会让你"看到更多"。

3.5 Auto Research：时间、并行度、资源

Agent 发展史被画成一条线：chatbot → +tools → DAG+tools → reliable single agent → multi-agent / fleet → 初步自我改进。Auto research 可调三个维度：时间长度、并行度、每任务资源——三者都 asymptote 于"多样性耗尽"，但理想情况下应该复利。

四、Building the Box：工程哲学与 Jump 数据栈

4.1 最小可工作的 closed system

Lucas 强调："If you're taking four days of compute per job, you might as well have the human do it." 正确的顺序是：先有最小可工作的 closed system → 快速迭代测可靠性 → 让它尽可能快 → 让小系统变鲁棒 → 然后再展开。

4.2 四条工程哲学定律

  • Gall's law：能工作的复杂系统必然源自能工作的简单系统。
  • Hyrum's law：用户足够多时，任何可观察的行为都会被某个人依赖。
  • Amdahl's law：单部分加速的天花板由它在整体里占的比重决定——所以并行 + 连接 boxes 比单纯优化单个 box 更重要。
  • Amara's law：技术的影响总是短期被高估、长期被低估（在 agentic 场景里叫 capability overhang）。

4.3 Scorecard 而非单指标

真实系统不是单指标。Lucas 展示了一张"匿名真实 scorecard"——多指标 Pareto frontier 加阈值、约束、trade-off 的矩阵。自动研究只盯一个 metric 会崩坏其他维度——难点不在 agent，在 scorecard 的可表达性。

4.4 程序员的三大美德 + 第四

引自 Larry Wall：Laziness / Impatience / Hubris。Lucas 加了第四：Righteous anger——系统变强不能变慢。

4.5 Jump 数据栈：凭什么做这件事

15+ 年的 packet capture 原始数据；自定义网络精确测量每条交易所间的光速差；point-in-time 重建；独立研究系统可模拟任意 capture profile。这套栈决定了 Jump 可以在 production-grade fidelity 上做 agent 研究。

五、Takeaways

1. 把 harness 设计匹配任务——能简单就简单；需要复杂角色时明确定义 roles。 2. 一切以 eval 支撑——point-in-time / artifact 来源 / scorecard 维度都要在 eval 里被捕获。 3. Bound the process——多 agent 团队的风险由"系统能通信什么"决定，不是由其内部决定。 4. Auto research in place 之后，建 box：从小 steerable 版本起步 → 一般化 → 连接 boxes → 最一般化系统。
