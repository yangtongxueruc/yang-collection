为什么 ML 需要一门新编程语言：Chris Lattner 谈 Mojo

节目：Signals & Threads（Jane Street）· Episode 25 主播：Ron Minsky（Jane Street） 嘉宾：Chris Lattner（LLVM / Clang / Swift / MLIR / OpenCL 创造者，Modular 联合创始人，Mojo 语言设计者） 时长：约 73 分钟（2025-09-03） 官方逐字稿：https://signalsandthreads.com/why-ml-needs-a-new-programming-language/

这是一期相当硬核的工程访谈。Chris Lattner 从自己的来路讲起，一路推到「为什么 AI 时代需要一门新语言、而 Mojo 想怎么解决它」。核心结论一句话概括：AI 带来了 GPU / TPU / ASIC 这类全新的异构算力，但行业没有「AI 界的 LLVM」，于是每家硬件公司都在各建垂直栈、碎片化严重；Mojo 的思路是用一门「像 Python 但有真实类型」的语言，把编译时元编程（metaprogramming）做对，从而同时拿到极致性能、跨硬件可移植性和易用性。

一、来路：编译器与语言设计的往返

Chris 在 80 年代用 BASIC 入门，靠书和杂志学编程，OS 课让他第一次体验「一层层搭系统」，波特兰州立大学的编译器教授把他带进了编译器世界。他的职业生涯在编译器工程和语言设计之间反复横跳：LLVM（2000 年启动）→ 2005 年加入 Apple → 2010 年前后 Clang 支持 C++ 自举 → Swift。他自认「不是数学家」，语言设计的取向是 utility-forward（从实用出发），而非从类型理论的数学美感出发；他认为能落地的特性（如 pattern matching、代数数据类型）才是推动主流采用的关键。

他还点出一个反复出现的隐喻——「系统里的沙子」：很多复杂源于本不该存在的约束（比如 C++ 永远无法删特性、Swift 里也有几粒沙子）。这也是他后来想做「下一代系统」去根治这些问题的动力。

二、为什么 ML 需要新语言：结构性的行业困局

真正的转折是 AI 来了。GPU、TPU、FPGA、ASIC 带来了全新一代算力，而「LLVM 从没真正在这套系统里工作过」。

Chris 把问题定性为一个结构性产业问题：

  • 做高级代码生成（先进 GPU kernel 等）的人，全在硬件公司里；每家都被迫自建垂直软件栈，因为「没有东西可插」——不存在「AI 界的 LLVM」。
  • 硬件公司自然只为自己的芯片优化，没人 incentive 去协作：AMD 不会去给 NVIDIA GPU 打工。于是跨厂商碎片化不可避免。
  • 低层语言（CUDA / ROCm / XLA）和高层工具（PyTorch / JAX / Triton）之间，跨平台支持「complicated, messy and incomplete」。
  • 在「两个本就不兼容的东西」上叠抽象（当年的 MLOps 热：在 TensorFlow/PyTorch 上盖一层 Python 做统一平台）只能加胶带——一旦出问题，就得调试一整座你根本不想懂的栈。

硬件侧也在变：现代 GPU 有 SM、warp（通常 32 线程 lockstep 的 SIMD 模型）、以及为矩阵乘专设的 tensor core；Chris 直言「CUDA 从不是为这个现代世界设计的，它设计时世界简单得多，20 年过去了没能追上」。再往外，Google TPU 干脆拿掉线程、把整颗芯片围绕大矩阵乘单元构建，更专用、吞吐更高。

三、Modular 的打法：不卖语言，卖平台

Ron 问了一个尖锐的商业问题：卖编程语言的公司「尸横遍野」，Modular 怎么避免被单一厂商锁定、又能做成共享平台？

Chris 的回答很直接：「First answer is, don't sell a programming language.」 Mojo 免费随便用，他们卖的不是语言，而是统一硬件的基础技术；等底座修好，再向企业卖高价值服务（管理数百到数千张 GPU、3 年云承诺、平台团队 + 产品团队的生产负载）。

技术栈由内到外三层：

  • Mojo：编程语言（最内层）
  • MAX：可视为 PyTorch / vLLM 的替代品，单机高性能 LLM serving
  • Mammoth：集群管理 / Kubernetes 层

四、Mojo 的设计哲学：Python 家族 + 元编程

回到 Mojo 本身。Chris 强调 Mojo 是 Python 家族的一员——这对部分人「polarizing」，但 AI 社区早已 Pythonic，这是巨大优势。设计上：

  • 元编程（metaprogramming）是性能的老解法：普通 for 循环在运行时执行，但高层类型系统希望在编译时也能跑代码。很多语言都有这种「运行时 / 编译时双语言」的割裂（C++ 模板、宏最严重）。写解释器很慢，理想是「boil away the control structure」，直接 emit 你想要的机器码。
  • Mojo 的追求是「一种语言、一套类型系统」同时覆盖编译时生成与运行时行为，两层调试体验一致。
  • 它看起来像 Python，但有真实类型；即便不用花哨特性，光用 CPU 的 SIMD 也能快很多（Chris 说「a thousand times faster or something」）。
  • 警惕 「sufficiently smart compiler（足够聪明的编译器）」陷阱：靠「魔法」让 demo 好看、声称编译器会自动搞定一切——但魔法不存在（当年的 auto-parallelization 就是例子）。CPU 本身是「让顺序代码并行跑得快的魔法盒」，代价是功耗与低效；Mojo 选择回到简单、把控制权交还给程序员。

五、性能与可移植性：类型系统与 PTX 类比

关于「可移植性能」：Chris 批评很多 AI 编译器只从一个很烂的基线往上爬，从不测量芯片的「speed of light（光速）」。而且硬件差异是真实的——AMD 的 warp 是 64 线程、NVIDIA 是 32；甚至 NVIDIA 内部 float32 与 float4 的 tensor core 行为也不同。Chris 还拿 1.2-bit 浮点当例子调侃「这真的是开玩笑吗」。要驾驭这种复杂度，需要强大的元编程。

关键设计落点：

  • 用抽象表示不同硬件，在编译时按所在硬件条件执行；布局不是简单 int，而是递归的层级树。
  • 类型 / traits（类似 Swift 的 protocol、Rust 的 trait、Haskell 的 type class）实现 ad hoc 多态——典型例子是 iterator trait，可泛型地套用在链表、数组、字典、网络包序列上。比 C++ 模板好得多：模板本质只是代码生成（像 C 宏），嵌套展开报错会「spectacularly explode」，且编译极慢（同样代码反复生成）；Mojo 能在不实例化的情况下检查泛型代码，把错误压到最小。
  • 可移植性机制：编译器解析你的代码时是泛型的、根本不知道目标平台；mojo build 默认产出普通 a.out，但 Mojo package 保留可移植性（类似 Java bytecode 的思路，但类型系统完全不同）。
  • 与 NVIDIA PTX 的类比：PTX 是可移植字节码（IR），驱动内的 assembler 把它编译到特定机器码 SASS（且 NVIDIA 故意不完全公开）。PTX 是个很底层的虚拟机，类型系统「无聊」（只有指针/寄存器/内存）；而 Java 靠 bytecode 暴露对象实现可移植。Chris 指出 Mojo 的特别之处：在可移植对象里保留了程序员驱动的特化指令（部分编译），控制权更强——不像 PTX 把机器相关细节完全从程序员手里拿走。

六、保持简单：语言演化的取舍

怎么在「需要精确类型控制」和「保留 Python 式简单」之间平衡？Chris 的经验：

  • 从 Python 起，管理层就能 push back：「先把 Python 生态的完整能力（list、for-comprehension 等）实现好，别急着发明随机特性」。
  • 对复杂性有反向压力：用元编程吸收本会散落各处的复杂度。他认同 Ron 说的 「power-to-weight ratio（功率重量比）」——语言设计要维持性价比。
  • Swift 的教训：早期开放设计流程（任何人可提 proposal）导致特性膨胀。Mojo 的反制是核心团队要小、刻意，不为「将来也许有用」而堆特性。
  • 向后兼容：主张语义化版本（1.0 / 2.0 / 3.0 可互不兼容但能链接）。对比 Python 2→3 花了 15 年（必须先把整个包生态转完），而 C++ 的 ABI 做对了。强类型系统能给出精确指引；强类型 + agentic coding 组合极佳——改个类型，让 AI「去跑下所有类型错误并修掉」，效果出奇好。Rust 在 crate / API 稳定化上的做法也值得借鉴。

七、Agentic 编程、开源与 Mojo 的当下/未来

开源与 AI 编码：Mojo 开源，有数十万行公开代码（含大量 GPU kernel）。好处不是「训练模型认这门语言」，而是让 Cursor 之类的 coding tool 去索引这个仓库来学——"having access to it enables it to do good work"。Chris 特别强调要按官方文档正确配置索引。

Mojo 是什么、现在能干什么：

  • 定位有过演变：早期更多谈「Python 的扩展 / 演化 / 最终替代」，近期更多作为「CUDA 的替代、自顶向下的 GPU kernel 全栈」。
  • 当下最实在的用途：让代码跑快（CPU / GPU 都行）；以及——扩展 Python 的最佳方式（预览中，即将固化）：把慢的 for 循环挪到 Mojo，没有 FFI / nanobind 那种绑定复杂度，pip 体验顺滑。有人把纯 Python 迁过去后，在 CPU 上拿到 10x / 100x / 1000x 加速。
  • 结尾 Chris 的总结：「let's solve heterogeneous compute and AI」—— heterogeneous compute（异构计算）才是那个真正有用、也足够有野心的目标。

一句话总结

AI 把异构算力（GPU/TPU/ASIC）推到前台，却没有人做「AI 界的 LLVM」，导致硬件厂商各自圈地、跨平台支持一团糟；Chris Lattner 的答案是 Mojo——一门「像 Python 但有真实类型」的语言，用做对的编译时元编程 + traits 类型系统，把极致性能、跨硬件可移植性和易用性塞进同一种语言里，并用「不卖语言、卖平台」的打法避开编程语言生意的坟墓。
