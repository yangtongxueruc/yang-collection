导语

这期节目的题目叫「Learning Goals and the Goals of Learning」——学习目标，以及学习这件事本身的目标。它表面上是一期教育话题，实际上是一条很硬的暗线：当写代码变成最便宜的一步，工程组织里「什么能力才值钱」需要被重新定价。

Aaron Bauer 的岗位本身就是这件事的产物。他是 Jane Street 少数几位「开发者教育者」（developer educator）之一——一半时间写代码，一半时间教别人怎么写代码，去教的对象是「自己公司的语言、自己公司的版本控制、自己公司的编辑器」。而当 LLM 可以把练习题直接做掉时，他面对的问题就变成了本集的核心张力：

「当你教别人用一个陌生的库时，LLM 其实可以直接替他写出来。那么这门库到底有什么是人真正需要知道的？又有哪些你会认为是样板，不必学？」（[59:46]）

这期最值得记的几条判断：

「造出一个看起来很像样的 PR 的成本已经几乎降到零，而验证它的成本基本没变、甚至更糟。」（[51:33]）
「简单到适合学习者去做、又难到 LLM 无法一次搞定的那类问题，现在已经接近空集。」（[62:14]）
「有时候让教育过程奏效的关键之一，就是刻意收走某些可供性（withhold certain affordances）。」（[62:55]）

本文基于完整逐字稿整理，所有论断都能在逐字稿页对应到时间点。

TL;DR：这期真正回答了哪些问题

  1. 「翻转课堂」被高估，「现场讲授」被低估。 Ron 的直觉是：讲座是一种表演，人在现场会被聚焦注意力；Aaron 认同——而且因为它是「活的」，你更可能记笔记，而记笔记本身就算从不再看，也真的有助于记忆。（[09:53] [10:43] [11:32]）
  2. 屏幕是注意力的头号杀手，而不是「打字」。 Aaron 说他在课堂观察到的关键不是手写 vs 打字，而是「人面前有块屏幕」——那会让大约一半的人即使想专注也做不到；这也是他尽量避免在计算机实验室里上课的原因。（[12:21] [13:10]）
  3. 「掌握式学习」在大学里必须打折。 无限次重试、取最好成绩、题序与选项顺序随机以防硬刷——但截止时间必须全程设置，因为学生会拖延，让人把作业堆到最后是失职。（[17:15] [18:54] [19:44]）
  4. 开发者教育者的岗位设计是 50/50，且「教学者必须是实践者」。 不在同一个生态里做同一件事，教不出有说服力的内容；而且这个岗位极难招——教学经验多的人在学术界且不愿离开，「优秀教育者 × 可信的 Jane Street 工程师」的交集很小。（[22:59] [23:49] [25:27]）
  5. 编辑器是 Jane Street 软件工程师的「主场」（home base）。 代码评审、版本控制、理解代码、讨论代码都发生在编辑器里；因为公司不用 git 而用自研的 Iron，反而必须有一支团队把集成做进编辑器。（[34:28] [35:15]）
  6. 自研与上游之间是两股互相剪切的力量。 一方面「你不用写的代码才是最好的代码」，回馈上游能让别人替你修 bug；另一方面 25 年的自研工具走出了完全不同的设计取舍——Iron 对「堆叠式 PR」支持极好，编辑 diff 的体验却很差。（[45:04] [32:50]）
  7. AI 改变的是「怎么写」，没改变「怎么读」。 很多工程师已经不太敲代码，更多在写提示词；但他们仍在读代码、看类型、看定义。遥测数据显示「跳转定义」的人均次数不降反升——可能与需要读、需要理解的代码变多有关。（[49:07] [50:45]）
  8. 瓶颈从「写」移到了「读与验证」。 LLM 生成的 feature 非常「顺滑」，那些你以为是问题征兆的破绽线索根本不存在——但它们往往还是坏的一塌糊涂。评审因此成为整个工作流里的 rate-limiting step。（[52:22] [58:06]）
  9. 「让它全写完我最后再读」可能不是最优解。 Claude Code 的 learning 输出风格会让模型中途停下、留一个 to-do 给人补；Aaron 用它之后觉得产出更愉快，而且确实更理解最终代码。这呼应了「用铅笔做笔记」的效用：参与生产过程会让你最后更懂它。（[53:11] [54:48] [55:37]）
  10. 「学习目标」是一种可复制的工程化写法。 句式是「完成这门 teach-in 后，学生将能够……」，后面接主动动词短语；「理解 property-based testing」不合格，因为它无法衡量。它还会逼你想清楚不想达成什么，并从目标倒推课程活动与背景材料。（[77:07] [77:57] [78:46]）
  11. 认知负荷是课程设计的实操抓手。 旧版 OCaml Boot Camp 一上来同时压上「学 OCaml + 学新编辑器 + 学新版本控制与评审系统」；拆开之后，先只学语法（Utop / 浏览器内编辑框），再单独认识编辑器、单独练版本控制，最后才合到一起。（[82:55] [83:43]）
  12. 在 AI 时代，Jane Street 把实习生课程围绕「测试、设计、代码评审」重建。 过去「能产出一批好代码」可能最重要，现在重要度下降；项目被改得更开放、更需要需求收集与设计；并首次让实习生做代码评审，为此加了三天专门培训（预制 feature + 参考答案 + 小组讨论 + 互相评审）。（[85:22] [86:11] [88:40] [89:29]）

一、从「海滩上的老师」到开发者教育者

Aaron 的路径是个很典型的「两条线交汇」：

  • 高中前的暑期科学项目去新墨西哥六周，学数学、天文、物理和一点 Python，用望远镜观测小行星再写代码算轨道——「进去的时候觉得这些都有意思，出来的时候发现编程好玩太多了」。（[00:01] [00:51]）
  • 小镇高中没有 AP 计算机课，于是通过北卡州的线上课程项目，跟一位在海滩上的退休老师学。（[01:41]）
  • 本科做 Fortran 的撞击模拟（其代码源头是计算早期模拟原子爆炸的程序——两种情形的物理差别不大），也谈到了自动微分其实可以追溯到早期 Fortran 编译器：能做一阶导，二阶导就「自求多福」。他的自嘲很到位：「我编程不是因为我热爱编程，我把它当工具用，因为它总比计算尺强。」（[02:30] [03:19]）
  • 本科最后一年被「渲染」迷住，于是读博；进项目后发现渲染研究已经成熟、剩余工作多在产业界，便「被惯性推着」继续，转做游戏设计研究与 CS 教育研究，博士论文研究人机问题求解：以科学发现游戏 Foldit 为对象，看玩家如何解题、协作、与自动化工具配合。（[04:09] [04:59]）
  • Foldit 的关键分工很值得玩味：人类贡献大尺度几何直觉，计算机负责「把蛋白质反复扭来扭去」找局部能量最低点，两者结合解出了实验室多年未解的结构；后来玩家甚至开始设计新蛋白——「不过 AlphaFold 之类后来把它的饭碗抢了」。（[05:48]）

之后就进入教育：Carleton College 先当面教两个学期，2020 年春季起连续四个学期线上教学——「这算是很 hardcore 的教学入门了」。（[06:38]）

二、疫情课堂里被验证与被修正的教学法

纯文本的失败与「翻转课堂」的流行

线上初期他照搬自己高中那门「纯文本、无视频」的线上 AP CS 模式（理由很正当：大家在家，不是每个人都有好网络）。结果立刻被反馈打脸：「对我很好用，但不是对所有学生都管用。」（[07:26]）

于是试了翻转课堂、同步课、拆小组。他也花了几句话把术语讲清楚：翻转课堂是把「讲」提前录好放到课前，把课堂时间留给练习与讨论——它不是疫情才有的新想法，只是疫情让它突然普及。（[08:16] [09:04]）

「为讲座辩护」

Ron 抛出一个很漂亮的辩护：人们低估了讲座的力量——讲座是一种表演，现场有种更打动人的东西；「你当然可以把该主题下最好的那堂课录下来看就行了」这个推论在真实的人、真实的环境里并不成立。Aaron 认同并补了机制：现场有聚焦注意力的效果，而且因为它是「活的」，你更可能记笔记；反过来，一个人对着你讲满一小时，参与感会流失、开始起反作用。（[09:53] [10:43]）

他甚至自己的做法也不是严格翻转，而是让课堂时间混合互动活动与少量讲授。（[09:53]）

记笔记、屏幕与「把电脑挪开」

关于「手写优于打字」的研究，Aaron 的说法很克制：就他的课堂经验而言，关键也许不在打字本身，而在于人面前有块屏幕——人类创造的一切信息与干扰夹在他和讲者之间，注意力就被削弱了。所以「大约 50% 的人即使想专注也做不到」，这也是他回避计算机实验室教学的原因。（[12:21] [13:10]）

Ron 接着讲了自家教小孩编程的做法：在纸上写程序、在餐厅等菜时给一段名字混淆过的 Scheme 程序让孩子猜「flub 干了什么」。要点在于：

「一旦给他们一台电脑去敲进去、跑出来，他们就在玩『让电脑做成一件事』的游戏，而不再思考『究竟发生了什么』。」（[13:58]）

Aaron 把它归纳成初学者一定会做的事——「这是给机器的神秘指令，我就随便乱改，直到它做出我想要的结果」；在屏幕上能直接跑时，这么做太容易了。（[14:47]）

掌握式学习与自动反馈

疫情期间他大量试验自动反馈：多选自动判分、填空、自动判题作业，目标是把「交作业 → 拿反馈」的延迟压到最短。他的不满很具体：传统模式下批改要一两周，那时学生早已往前走，甚至不会看反馈。（[16:25]）

同时引入掌握式学习：同一知识点可尝试任意多次、取最好成绩、直到真正做对；题序与选项顺序不断变化以防硬刷——「真的想全部理解、然后拿 100% 反而更快」。但他在大学场景做了折扣：截止时间必须全程设置，因为学生会拖延，「让人把作业堆到最后是一种失职」。（[17:15] [18:54] [19:44]）

关于 LLM 生成即时反馈，他给了一个很务实的判断：潜力很大，但要收窄场景——比如针对代码风格而不是一篇议论文；做法上可以叠加测试用例自动判题 + linter 规则提示 + 一层代码风格检查。同时警告 LLM 会给出大量误导性误报，至少要向学生交代清楚。（[20:33]）

三、这个岗位是怎么被发明出来的

从明尼苏达搬到布鲁克林（为了离弟弟近一些），恰好撞上 Jane Street 在招「教育者 + 程序员」这个奇怪组合。（[21:21]）

Ron 交代了岗位背后的逻辑：教学在这家公司一直是重要的事。原因有两层——主题层面，没人进来就懂交易；技术栈层面，这家公司自有的语言、版本控制、编辑器「在不少方面都很怪」，必须长期投入教育。（[22:11]）

关键设计有三条：

  1. 50/50：一半时间写代码，一半时间做教育（直接授课、开发课程，以及帮别人成为更好的老师——「我们不希望有一小撮开发者教育者包办所有教学」）。（[23:49]）
  2. 教学者必须是实践者：如果参与的人不身处同一个生态、不做同一件事，他们就教不出有效、有说服力的内容。（[23:49]）
  3. 招聘极难：Ron 期待「优秀候选人从天而降」，结果完全没有。原因很结构化——教学经验多的人大多在学术界且不想离开；同时要「既是优秀教育者、又是完全可信的 Jane Street 工程师」，这个交集很小。（[24:38] [25:27]）

Aaron 补充了 50/50 的真正价值：这个人把教育当成工作的第一优先级，并且对教育保持持续关注——这是「台阶式的变化」，也是这件事能成的原因之一。（[26:16]）

岗位还在扩张：OxCaml 教育者、机器学习教育者，以及通用型开发者教育者。他在这里说了一段很像「工程师成长观」的话：

「语言数量少的时候，你可以走进任何代码库做事情。一旦有两三四种语言，就会出现自然的分层……我非常希望公司里没有『OCaml 程序员』和『Python 程序员』，只有软件工程师——他们懂得使用多种工具，并能判断该用哪个。」（[28:45]）

他也担心「人被困在自己的工具里」，并预言教育者未来的形态会像设计师一样嵌入各团队：比如有一位教育者坐在 AI 助手团队里，既服务那个方向的教学材料需求，也让教育者积累多样化的技术经验——「如果把他们全塞进公司的同一个角落，他们的背景就都一样了，那是一种更不牢靠的基础」。（[30:23]）

四、编辑器为什么需要一支团队

Aaron 在 tools and compilers 组下的 editors 团队，维护 VS Code、Emacs、Neovim，以及代码索引服务和 OCaml language server。他早期在 Iron（公司的 feature 管理软件）上写扩展，让「把工作拆成多块、排成关系链、分别过评审」从繁琐手工变成顺手的工具。（[31:11] [32:01]）

在 Jane Street，「feature」大致介于外界的 commit 与 PR 之间。（[32:01]）

平行宇宙里的开发工具

Ron 的说法很直白：

「Iron 比外面所有东西都好得多，同时在某些具体方面又差得多——取决于你想看哪一点。」（[32:50]）

好的那一面：对「堆叠式 PR（stacked PRs）」的支持是内建的基础能力。差的那一面：真正去编辑 diff、来回搬动东西的过程又慢又痛苦——「你甚至会更愿意用 Emacs 的 Magit，也不愿意用我们已有的那套」。（[32:50]）

结论是：通往同一个大目标可以有很多技术路径，最后会得到非常不同的功能组合，并由此流淌出一整套工程文化——你怎么做代码评审、怎么提反馈，完全被底层技术系统塑造。（[33:39]）

编辑器就是 home base

Jane Street 把文本编辑器当成工程师的主场：评审、版本控制等所有交互都在编辑器内，全部可键盘导航，不需要在应用/页面之间跳。也因为公司「不走寻常路」（不用 git 用 Iron），反而必须有一支团队把这些集成做进编辑器，让人真的能「住在里面」。（[34:28] [35:15]）

对比很鲜明：Jane Street 明显不是 web-first 的组织，而大厂「最后都相当重地把这些交互全都塞进了浏览器」。（[35:15]）

另一个早期设计选择很有信息量：对改动的反馈以特定格式写在编辑器里（他们管这些注释叫 CR），而不是去某个网页 UI 给别人的 PR 留言。更进一步——因为人在编辑器里，协作时你可能直接把问题改掉，而不是只留一条评论：

「这对外来者会显得『不卫生』：就像别人伸手进来修改我的 PR。但无论好坏——它只是另一种模态、另一种在思考代码过程中互动的方式。」（[36:52]）

规模带来的技术债

编辑器团日常最真实的一类问题来自「规模」：

  • 巨型 diff 打爆 VS Code 的 diff 算法性能；更糟的是，打开巨大 diff 卡住再关掉，会把查看 diff 的队列整体锁死，之后所有 diff 都看不了。（[37:40] [38:30]）
  • 集成 Iron 的 code view 打破了 VS Code 对缓冲区 URI 的假设，导致内置搜索行为异常，需要逐个排查修复。（[39:18]）
  • 索引：为了让编译器产物更好地支持 module 查找，有人往索引里加了额外信息；结果这个索引多用好几 GB 内存，机器上已经建不出来了。（[40:07]）

Aaron 由此总结出一个规律：编辑器是许多东西到达用户面前的界面，所以问题常常在类型查询系统或索引系统里，而你去修的地方可能在评审系统，也可能在 OCaml 语言那一侧。（[40:57]）

Python notebook：又一个「自己造」的案例

交易与研究同事用 Python 的主要界面是 notebook，而这块一直非常棘手：各种方案各有明显缺陷，甚至连「人们为什么用 A 不用 B」都难以搞清楚；还出现「新方案本想取代旧方案、却缺了旧功能，结果同时维护好几套」的不幸趋势。更本质的痛点是代码不易共享——想把代码抽成 repo 里的 Python 库供多个 notebook 复用，就需要一个「编辑 .py 和编辑 notebook 一样方便」的环境，而 VS Code 在内部 notebook 场景下性能与可用性都很吃力。（[41:45] [42:34]）

于是他们开始自己造——「这是 Jane Street 很多工具工作的主题。我也确实很担心我们会过度偏向自建」；但反过来，「完全掌控、并且所有东西都建在一个你从上到下都理解的生态里，本身有很大力量」。他形容这是两股方向相反的力量在互相剪切。（[43:24] [44:14]）

他也给了上游的定价：

「你不用写的代码，才是最好的代码……而且不只是你不用写，还有大量其他人在用它、报告问题，而这些问题会被修掉。」（[45:04]）

反向的力量同样真实：他们大量扩展是用 OCaml 写的（跨 Neovim / Emacs / VS Code），非常不「标准」；而 elisp 与 ecaml 之间的边界、尤其涉及异步的部分相当别扭，长期目标是重新架构以减少奇怪死锁——而把两种语言的并发原语「联姻」，本身就极难，Python 与 OCaml 之间也撞上过同类问题。（[46:37] [47:27] [48:17]）

五、agentic AI 之后：编辑器团队该造什么？

这一节是本集信息密度最高的部分。Ron 问得很直接：真正好用的编程智能体出现后，你对编辑器的判断变了吗？

Aaron 的答案是「信念没变、事实变了」：

  • 没变：编辑器仍然是软件工程师极好的主场；新工作流应当像旧工作方式一样自然、可及地通过编辑器完成。（[49:07]）
  • 变了：「写代码」在变，「读代码」没变。 很多工程师已经不太亲手敲代码，大部分键入变成了写提示词；但他们仍在读代码、看类型、看定义。（[49:07]）

这给做编辑器的人带来巨大不确定性：「现在造什么才是有用的？一年之后什么还会有用？还会有什么用吗？」（[49:57]）

用遥测数据回答「工作方式到底怎么变了」

他们加强了编辑器遥测与可观测性，看人们在编辑器里做什么、如何与 OCaml language server 交互。一个很漂亮的例子：

「我原本的假设是：如果 LLM 产出的代码很好、人不再需要频繁查 API，那么人均跳转定义的次数应该减少。但在遥测数据里，看起来反而是略微增加了。这相当出人意料，但也可能是因为人们实际上需要读、需要理解的代码比以前更多了。」（[50:45]）

因此「该不该努力把跳转定义做快」这类问题，答案应该由数据给出，而不是靠猜。——「你提出的『用数据驱动』比我本能想『凭空推理』更对。」（[51:33]）

成本结构变了：造 PR 趋零，验证不变

Ron 引用了 Charlie Marsh 的一个说法，这是本集最锋利的一句：

「造出一个看似合理的 PR 的成本已经几乎降到零，而验证它的成本基本没变、甚至可能更糟。」（[51:33]）

他进一步描述了 LLM 生成代码那种「说不出的诡异感」：非常平滑、非常漂亮，许多你以为是问题征兆的破绽线索根本不存在，但它们往往还是坏得一塌糊涂。所以「阅读和理解」至少与过去不同、在某些方面确实更难；「投入更多工程精力让人更容易理解正在发生什么」因此变得非常重要。（[52:22]）

他也提醒不要低估「硬办法」的价值——跳转定义、推断出的类型、测试结果这类从代码里抽取数据并呈现出来的能力。（[53:11]）

Claude Code 的 learning 模式与「心智模型」

Aaron 谈了他自己在教育工作里试过的 Claude Code learning 输出风格：修改系统提示词，让模型有时停下来，在代码里留一条要给人类补的 to-do。他的体验是双向的：产出过程更愉快，而且更有效地真正理解了它产出的东西。（[53:11] [54:00]）

他由此提出一个更大的探索方向：不只是在「产出端」加解释工具，而是思考在模型产出代码的过程中，人应该怎么与它交互，才能最终形成扎实理解：

「『让它全写完、我最后再读』感觉更高效，但我现在有点怀疑那是否真的是最优做法。」（[54:48]）

Ron 在这里给出了一个很漂亮的类比——用铅笔做笔记的效用：你亲身参与「生产过程」，会让你最后更好地理解它；而当前工具的一切都偏向「模型生成代码，然后你决定要不要接受」，这也许是错的。（[54:48]）

Aaron 的连接更直接：他给学生讲代码评审时做过一页幻灯片——你写代码时在逐步建立理解、发现错误时在修正心智模型；而你评审别人的代码时，对方直接给你成品，你只能别扭地重建一套心智模型。「我当场意识到：等等，这正是与 LLM 协作的样子——它让你更难对自己在编写的代码形成心智模型。」（[55:37]）

一些具体的产品设想

Ron 认为这里创新空间很大：「把人放进自动化里的导师行为」变得极其便宜——过去你得去找另一个人才能得到这种体验。（[56:27]）

他还提出一个三年前完全说不通的设想：让 feature 随附一个「为理解这个 diff 而定制的可视化」，它就直接出现在评审中间。（[56:27]）

Aaron 顺着补充：也可以把预计算好的代码切分与逐块解释「烤」进 feature，评审时一键调出；否则你得选中一段、让模型解释，那有额外摩擦，响应也未必快。（[57:16]）

Ron 把这总结为软件工程师的「当代境况」（他说「当代」指的是最近八个月左右）：评审占你时间的比例大幅上升，于是「把它做得更好」的价值突然飙升——「它现在更明确地成了整件事的瓶颈环节」。（[58:06]）

六、当 LLM 能把练习题做掉，还教什么？

张力：这个库，人到底需要懂什么？

测试 teach-in 教人使用各种库——property-based testing、测试中时间的确定性控制。问题立刻出现：「当你教人用一个陌生的库时，LLM 可以直接替他写出来。那这门库有什么是人真正需要知道的？哪些只是可以丢给模型的样板？」（[59:46]）

目前的选择是：

「人得把这些想清楚、并且自己实现一遍——至少一次——对于最终形成足够的理解其实相当重要。即便之后他们只是读 LLM 初写的应用，那次亲手做过，也是后续能评判这些东西的关键输入。」（[60:36]）

同时要重新划线：过去那些「因为不得不做」的繁琐劳动，也许不必再让人学着做了。（[61:26]）

「接近空集」与「刻意收走可供性」

真正难的是教什么、怎么教：怎么有效使用这些工具、如何融入工作流、哪些做法会让你被带歪。他承认这还在极早期，没有定论，工具变化极快——但问题已经可见：「确实有人栽跟头：氛围编程得太狠，用 LLM 生成东西却不动脑子。这是个真问题——你仍然需要思考。」（[61:26] [62:14]）

接着是 Ron 的两个重量级判断：

「学习的核心之一就是与材料搏斗。而一个你随时有个精灵随叫随到、可以直接召唤来解决问题的世界，本身就是个真问题。」（[62:14]）
「简单到适合学习者去做、又难到 LLM 一次做不掉这两类问题的交集，现在已经接近空集。」（[62:14]）

以及那条从「纸和笔」延续下来的原则：

「有时候让教育过程奏效的关键之一，就是刻意收走某些可供性。我担心我们面对的是一整代在全新环境里学习的人，而我们自己都不知道该怎么办：不知道该提供哪些可供性、该收走哪些。」（[62:55]）

Aaron 补充了他们在实践中反复撞上的同一个坑：任务范围定不准——要么要求人产出远超其打磨时间的代码量（那就无法传达「这段代码归你所有、必须仔细审」这一课），要么大到消化不完。（[63:04] [63:54]）

他对未来的判断是：几乎必然会出现一种结构——某些环节不用 LLM、某些环节用；而「怎么配对、各自要拿到什么」需要大量实验。他也提醒一个结构性问题：接下来的学习者可能自己没花多少时间敲过代码，某个核心学习机制也许体验不足，这可能最终改变「必须教什么」。（[64:44]）

训练营、teach-in 与「课程目录」

新人入职路径：OCaml Boot Camp（累计式练习，用 OCaml 搭一个小型 client-server 应用、学核心库、由导师评审代码并开始理解代码风格）→ Production Boot Camp（应用如何部署、监控、配置），构成上岗头两周；前者现在约一周能走完。OCaml Boot Camp 的早期版本大约有 20 年历史，近年被大幅打磨。（[67:13] [68:02] [68:52]）

教学法上他最强调的一点：新概念要在语境中引入——由具体应用、要加的功能来驱动，而不是先拿一个工具再去找它能解决什么问题：

「人们犯的错误是先引入一个工具，再去找它能解决的问题；而不是：我们现在要做这件事、没有好办法、等等，这里有这么个东西，我们为什么不用它？」（[69:42]）

第一年还有一系列 teach-in：测试、高性能 OCaml 与性能分析工具、系统调试、高级函数式编程；更专门的有 Bonsai（用 OCaml 写 web UI 的库）、market data 等。整体越来越像一份课程目录，由新人与其经理/团队一起规划第一年的学习路径；材料也被设计成支持自学。（[70:32] [71:20]）

关于「概念 vs 实用」，Ron 承认最初的愿景（用 Bonsai 教增量计算、用 market data 教流式数据与协议设计）效果不如预期，实际走向了更偏「给实用工具」。Aaron 的解释很深刻：

「我的同事本来就已经是很强的问题解决者——这里面显然有筛选效应。所以这里的教育会偏离大学那种『花大量时间啃一个棘手问题』……因为在工位上他们日常做的就是这件事；反过来『这里有些有用的工具，我们带你过一遍』会更有价值。有些概念课会以这种方式悄悄混进来——不是因为你围绕它设计，而是因为理解这个工具、并且会用，本身就要求你理解那些内容。」（[73:00] [74:38] [75:27]）

「学习目标」：一种可复制的写法

这是 Aaron 带到 Jane Street 最被认可的一件「外来经验」。（[76:17]）

写法很具体：句式是「在完成这门 teach-in 之后，学生将能够……」，后面接一串主动动词短语：

「『理解 property-based testing』不是好的学习目标，因为非常含糊、无法衡量。但『学生将能够针对例如嵌套 record 类型的输入写出一个 property-based 测试』就具体了——界定了复杂度、以及他们能做到的那类事情。」（[77:57]）

它有三层价值：

  1. 逼你想清边界：我到底想达成什么，以及我不想达成什么——哪些不是对学生时间的好安排。（[78:46]）
  2. 从目标倒推课程：学生最终要能做什么 → 课程里就该练习这些 → 再倒推需要哪些讲义/材料/代码片段。（[78:46] [79:36]）
  3. 让评估有对象：Jane Street 更关心评估课程本身有没有教会人，而不是评分学生——「你能看到最后人们是否能做到你希望他们做的事，这就是对自己工作的评估」。（[79:36] [80:26]）

他还说了一层更软的意义：学习目标其实也是一种心态——「学生最后会有什么不同？你今天为什么来上班？」他发现这个提问在面试潜在开发者教育者时特别好用：有的人能讲出深思熟虑的目标，有的人则只是「我喜欢这个材料，所以开了门课」——而后者也不该被苛责，因为大量好的教育并不关于流程，而关于魅力、想法、能不能把演出撑下来；但结构确实能帮到第一次开课的人。（[80:26] [81:16]）

认知负荷与主动学习

他有意把认知负荷用在 OCaml Boot Camp 上：旧版一上来就同时压上「学 OCaml + 学一个你可能没用过的编辑器 + 学一套你没用过的版本控制与评审系统」。拆开之后是：先在 Utop（命令行 REPL）或浏览器内编辑框里只学语法 → 再单独认识编辑器 → 再只围绕版本控制做练习 → 最后才合到一起。（[82:55] [83:43]）

另一条是主动学习：尽量让活动互动起来。今年夏天实习材料里的落地方式包括大量小组讨论、围绕设计的互动活动、以及练习与需求方对话——「把『学生彼此之间真的互动』当成教育过程中重要的一环」。（[84:32] [85:22]）

七、为 AI 重建实习生课程

触发点很直接：「哇，AI 工具现在真的强了。」 过去给实习生一上来做的那种四周项目，如今「一个提示词就做完了」——那既不是评估实习生的有用方式，也不是有意义的产出。（[85:22]）

于是做了四件结构性的事：

改动具体做法时间点
项目性质更开放，加入设计、需求收集等元素，更「难」、更贴近真实工作[85:22]
信号重定「能产出一批好代码」过去也许是最重要的信号，现在重要度下降[86:11]
新增主题测试（为数据库应用写高质量测试套件）；设计文档评审练习；「角色扮演需求方」的需求收集活动[87:01] [88:40]
代码评审入课首次让实习生评审代码，并在实习中期加三天专门培训[88:40] [89:29]

为什么测试在 AI 时代更重要？Aaron 给的理由很硬：

「测试一直重要，但现在在很多方面更重要了——因为模型靠反馈活着，你确实需要给它们判断『做的对不对』的方式。超出相对简单的问题之后，它们就是不会一次给出好答案。」（[87:50]）

代码评审的三天培训设计得很具体：实习生拿到预制好的 feature（给他们此前在测试/设计环节做过的同一个应用加功能）→ 自己写评审意见 → 对照一份「参考答案」（别人可能留下的那组评审意见）→ 小组讨论分歧 → 再实现自己的 feature 并互相评审，积累练习量，之后由导师和真实项目继续给他们发 feature 评审。（[89:29] [90:18]）

复盘：最大的坑是「范围」

「很多挑战都和『我们要求人做的事』的范围有关。如果我们让人产出的代码量远超其打磨时间，那就说不通了——我们也没传达出想要的那一课。」（[90:18] [91:06]）

同样的道理也适用于代码评审：给一个人一个过大、问题过多的 feature，他反而很难识别出你真正希望他注意的那些问题——「这大概又回到了认知负荷的问题」。（[91:06]）

真正被验证有效的：四人小组的频繁讨论

与 OCaml Boot Camp 的自定进度不同，新课程把实习生分成四人小组（pods），并明确在全程频繁安排小组讨论：「你是怎么用 LLM 工具的？」「它吐给你的测试里你看到什么问题？」Aaron 认为这些讨论（含全职导师参与）非常有成效，并希望把很大一部分实习生教育建立在这种模式上。（[91:55]）

其他待改进项：

  • 缩减任务范围 + 调整重点与节奏；尤其要处理好「跑得快的人」与「走得慢的人」各自该专注什么，并通过预期沟通让人真的花时间学最重要的东西，而不是为了赶进度而抢跑。（[92:44] [93:34]）
  • 起手顺序要改：早期某一批一上来就强调多任务并行与「氛围编程」，事后觉得那定错了基调；现在改为从「测试与高质量测试套件」入手。（[93:34] [94:24]）
  • 未来可能加入更多具体工作流指导（现在是「有一些注意事项与要警惕的东西」，但还没有「我们认为这是好的提示/交互方式」的结论）——这也是小组讨论的价值所在：大家在互相分享哪些技巧有用、哪些没用。（[95:10]）

最后一条判断很关键，也解释了为什么这件事没有标准答案：

「不仅变化快，而且两个人用同样的方式使用它，得到的结果可能也不一样。所以你给人一个涉及 LLM 的练习时，它给『他们做的时候会发生什么』引入的不确定性，比过去大得多。」（[95:59]）

八、可操作启示

访谈中的观点可以立刻做的事
参与生产过程才能形成心智模型（[54:48] [55:37]）用「learning 风格」提示词让模型中途停下、留 to-do 给人类补；把「我参与了多少」当作理解程度的代理指标
造 PR 趋零、验证不变（[51:33]）把工程投资从「生成」转向「理解与验证」：跳转定义、推断类型、测试结果、随 feature 交付的定制可视化
LLM 代码「无破绽却常坏」（[52:22]）不要把「看起来很顺滑」当质量信号；对 LLM 产出的 feature 建立独立的验证手段（测试、类型、评审清单）
评审判成瓶颈（[58:06]）把代码评审当作一等公民来建设与训练，而不是默认能力；给评审写「参考答案」用于校准
学习目标写法（[77:07] [77:57]）任何培训/文档先写「完成后学员将能够…… + 主动动词」；同时写明「不想达成什么」
认知负荷（[82:55]）新工具培训不要同时上「语言 + 编辑器 + 版本控制」；拆成独立环节，最后才合练
概念藏在工具里（[74:38]）想教架构理念时，不要设计「烧脑思辨题」，而是围绕一个真实有用的工具来组织
刻意收走可供性（[62:55]）明确课程里「哪一段不许用 LLM」；反之也要有一段必须用，并教怎么用
范围是最大的坑（[90:18] [91:06]）让练习的产出量与打磨时间匹配；评审练习的 feature 不要塞太多问题，否则学生抓不到重点
任务对 LLM 不能太简单（[62:14]）设计练习时先自测：这个任务 LLM 一次能不能做掉？能，就加大范围或改为开放性问题
